Every release PR in my repo failed CI.

And both tools involved were doing exactly what they promised.

The setup:
- Python services pin dependencies with uv.lock
- CI enforces "uv lock --check" so the lockfile can't drift from pyproject.toml
- release-please bumps the version in pyproject.toml on every release PR

The collision: uv.lock also records each package's own version. And release-please knows nothing about uv.

So every release PR shipped a pyproject.toml that disagreed with its own lockfile, and got blocked by the very hygiene check keeping the repo healthy.

The fix: teach the release workflow about the lockfile. A step re-locks the bumped packages on the release branch and pushes the sync commit back.

One wrinkle that matters: the push uses a PAT, not the default workflow token. Commits made with the default token don't trigger CI. And an untested sync commit on a release branch defeats the whole point.

The general rule I took away:

Any generated file derived from a version — lockfiles, chart versions, manifests — must be regenerated by the release automation itself.

Otherwise every release arrives broken by construction.
